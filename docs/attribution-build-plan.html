1

Ad-attributed revenue from the booking engine

This is the product's core claim, and it is far closer than the current dashboard suggests. A complete booking-attribution subsystem already exists — it has simply never been connected to a live hotel, which is why the report says "Bookings aren't connected yet" and every revenue figure falls back to the tracking snippet.

Already built
  • Booking — gross / net / room / ancillary / tax / refunded, idempotent on (hotel, provider, externalBookingId), so a webhook retry cannot duplicate revenue
  • BookingStatusEvent — append-only, so cancellations and refunds reconstruct realized revenue rather than overwriting it
  • BookingJourneyMatch — ten match methods graded DETERMINISTIC → STRONG → PARTIAL → UNKNOWN, with the compared evidence kept for audit
  • Cross-domain handoff — snippet v2.5 carries _ht_j to the booking host, 30-minute TTL. This is the fix for identity dying at the domain boundary
  • Hashed guest identity — email and phone hashed through the same salted chain as visitors, so matching never stores a raw contact detail
  • Push receiver with constant-time secret comparison, per-provider rate limiting, tenant resolution
Missing
  • The Simplotel adapter is a deliberate stub. It refuses to guess field names — its own comment says guessing produces "confident, wrong bookings and wrong revenue"
  • No BookingConnection row exists for Aster, and there is no UI anywhere to create one
  • Revenue on the report still reads TrackingEvent.conversionValue, not Booking
  • No decision yet on which match confidences count as ad-attributed revenue
The blocker is external, and it is the long pole. Everything here waits on two things only Simplotel can give: their actual webhook payload spec (field names for amounts, guest identifiers, reservation id), and confirmation that _ht_j survives the hand-off and comes back on the booking. Without the second, matching drops from DETERMINISTIC to email/phone hashes — which collide when a family books under one address. Open that conversation this week; it gates everything else in this workstream.

One design decision needs making before the numbers go in front of a hotel. Not every booking will match a journey. If "ad revenue" silently means "revenue we could match", the figure understates and nobody can tell by how much. The honest shape is three numbers side by side: attributed to ads, attributed elsewhere, and unmatched — with the third visible rather than absorbed. The grading ladder already exists to support exactly this; my recommendation is to count only DETERMINISTIC and STRONG as attributed, and show PARTIAL separately.

2

Calls from a per-hotel sheet

Mechanically solved — this shipped today and is live on Aster's report showing 519 calls. The question is only how a second hotel gets the same thing.

Already built
  • Apps Script push on an onChange trigger — an edit lands in seconds, workbook stays private
  • Daily CSV re-import as a self-healing backstop, so a dropped webhook is not permanent staleness
  • Reconciliation: a day whose disposition columns contradict its stored total is withheld, not added
  • Missing days stay missing — never counted as zero
  • Coverage warning on the report, which fires and clears itself automatically
Missing
  • Column layouts are hardcoded. cbh_v1 and three_hills_v1 are TypeScript constants listing exact column order
  • Sheet-to-property wiring exists only in a seed script — no UI
  • No status card anywhere. Meta, Google Ads, GA4 and Instagram each have one; the tracker has none — which is precisely why it sat seven days stale unnoticed
Fully in our control, and small. Today, onboarding a hotel whose sheet differs by one column means writing a new layout constant and deploying. That is fine for two properties and untenable at twenty. The fix is to move layouts from code to data — a header-mapping row per connection — plus a settings screen and a status card. Roughly a week, no external dependency, and it removes a deploy from every future onboarding.
3

Message counts from Meta

Built and rendering. Two problems, one fixable and one permanent.

Fixable
  • The campaign sync has been dead since 10 Sep. AdCampaignSnapshot rows arrive with a null messaging figure while account-level spend keeps flowing — so nothing looked broken
  • Diagnosing it needs database or log access, both currently closed to me
Permanent
  • Meta does not separate WhatsApp from Messenger and Instagram DM. One combined figure, no per-network breakdown exposed to connected tools
  • So a tile labelled "WhatsApp messages" fed from here can never be WhatsApp-only, however it is labelled
That second point is what makes workstream 4 necessary rather than merely nice. The Cloud API is the only route to a real WhatsApp-only number — and the only route to knowing who messaged, which is what turns a count into revenue.
4

Click-to-WhatsApp → booking attribution

Nothing exists yet. But less is needed than it appears, because the hard half — matching a contact detail to a booking without storing it — is already solved and in production use.

Reusable today
  • Booking.guestPhoneHash and guestEmailHash, already populated by the ingest path
  • The salted hash chain in lib/pii.ts — one function, both sides
  • phone_hash and email_hash are already match methods in the grading ladder
  • bookingChannel already carries whatsapp as a value
To build
  • WhatsApp Business Account + Cloud API access (Meta review)
  • Webhook receiver for inbound messages
  • ctwa_clid capture — the click-to-WhatsApp click id Meta attaches to a conversation that began from an ad
  • Phone normalisation to E.164 before hashing, or nothing will match
  • Booking-sheet ingest as the interim revenue source
Prioritise ctwa_clid over phone matching. Meta stamps it on the conversation itself, so it names the exact ad — that is DETERMINISTIC evidence. Phone matching is inference: two guests share a number more often than you would like, and a booking made by a travel agent carries the agent's. Build the click id as the primary key and keep phone as the fallback, exactly as the existing ladder is shaped.
Two things will bite. First, the number you connect to the Cloud API cannot already be in use on the WhatsApp app — if the property is running its bookings off a phone handset today, that number has to be migrated, and their current workflow changes. Get that agreed before any code. Second, this stores customer phone numbers under India's DPDP Act; the hashing design helps, but notice and purpose need to be right, and a hash cannot be un-hashed when someone asks what you hold on them.
